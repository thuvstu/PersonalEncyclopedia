## 3. 核心の発見 2点

### 3.1 発見A: 自動ハイパーリンクは「バックエンド完成・UI配線ゼロ」を4世代連続で繰り返している

GAS版`34_hyperlinks.js`の`buildLinkIndex()`はキーワード→行のインデックスを構築するが、WebApp本体`Index.html`からの呼び出しは**grep 0件**(本書執筆時に直接確認)。Python版`linker.py`(LearningHub→LMM)も同じくTrie実装。そしてPEの`AutoLinker.kt`も呼び出し元ゼロ(mismatch.md §1.2、本書§1.2で再確認済み)。

**これは単発の実装漏れではなく、構造的に起きやすいパターンである。** 対する採点パイプライン(§3.2)は同じく複数世代を経ているが、そのたびに完成度が上がっている。両者の違いは「呼び出し箇所の数」にあると考えられる——採点は「回答判定」という**単一の呼び出し口**に配線すれば機能するが、自動リンクは詳細画面・定義文・Wiki記事など**複数の表示面に同時に配線しないと体験として成立しない**。AGENTS.mdの「1セッション1機能」原則と、この「複数画面に同時着手が必要」という性質は相性が悪く、結果として「将来拡張」に先送りされ続けてきたと推測できる。

→ **対策は§5 Phase 2で、画面単位に明示的にセッション分解する。**

### 3.2 発見B: 採点パイプラインは3世代の改良を経て今のPEが最も完成度が高い

`grader.py`(LMM)は「正規化完全一致→Fuzzy(レーベンシュタイン)→セマンティック」の3段階。PEの採点パイプラインも「決定論→rubric→意味」の3段階で、テスト99本・`docs/新採点システム.txt`という設計根拠まで揃う(DESIGN.md §13.1)。**ここは既に十分強く、触る必要はない。**

### 4.2 転用してはいけないもの(明文化)

- **PostgreSQL/Docker/FastAPI常駐構成そのもの**(FablePKMENCY・GachiPKM・KNOS・LMM全てに共通)。無料・一人運用・10年利用という制約と本質的に相性が悪い。KNOSは自ら「予算:無料のみ」「一人で管理できる複雑度」と制約を書きながら、WSL2常時起動+Cloudflare Tunnelという運用負荷の高い構成を選び、それ自体が不採用の一因になったと考えられる(§2.1参照)。**PEの「Androidネイティブ+Room、PCは閲覧専用」という不変決定は、この失敗を正しく回避している。**
- CapacitorによるWebアプリのモバイルラップ(LMM)。Composeネイティブの操作性・オフライン性に劣る。
