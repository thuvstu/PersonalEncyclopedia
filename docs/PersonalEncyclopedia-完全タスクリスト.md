## 0. このリストの使い方

- 1タスク = コーディングエージェントに渡す1セッション分の粒度になるよう分割してある
- 各タスクは「なぜ」「完了の定義」「依存」を持つ。依存が終わっていないタスクには着手しない
- 既存ロジックに触れるタスク(🔧マーク)は、着手前に該当テストが存在することを確認する。存在しなければテストを先に書く
- 新規追加タスク(➕マーク)はテストなしで着手して構わない(壊すものがまだ無いため)
- 各フェーズの最後に「ここまでで実際に数日使ってみる」チェックポイントを置く。フェーズ哲学(§3.3)を形骸化させない

## フェーズ1: データ保護の穴を塞ぐ(不可逆リスク最優先)

> このフェーズの目的は機能追加ではなく「今、端末が壊れたら/次のアップデートを間違えたら、何もかも消える」という状態を脱すること

- [ ] **P1-1: 🛑 V-1で確認したビルド不能状態があれば直す**
  - なぜ: 他のどの作業も、ビルドが通らなければ検証できない
  - 完了の定義: ビルド成功。テストはまだ書かなくてよい(既存の壊れたコードを直すだけなので新規ロジック追加ではない)
  - 依存: V-1, V-2

- [ ] **P1-2: ➕ バックアップの端末外退避(SAF方式を優先)**
  - なぜ: コア要件2(Data-Permanent)が完全に未充足。最優先の負債
  - 方針: Drive API本採用ではなく、**SAF(Storage Access Framework)でユーザーが任意のクラウド同期フォルダ(Google Drive for Android・Dropbox等、既に端末に入っているもの)を指定し、そこへ暗号化ファイルを書き出す方式を推奨**。OAuth同意画面・トークンリフレッシュ・API審査を丸ごと回避でき、エコの3軸(特に認知コスト)により合致する
  - 完了の定義: `drivesync/`(または`externalBackup/`)パッケージを新設し、`BackupWorker`のTODOをSAF書き出し処理に接続。日次実行で暗号化ファイルがユーザー指定フォルダに生成されることを確認
  - 依存: P1-1

- [ ] **P1-3: ➕ バックアップ成功の可視化**
  - なぜ: 実装しただけでは「本当に毎日成功しているか」をユーザーが知る手段がない。サイレント失敗(認証切れ・フォルダ削除等)に気づけない設計は「実質的にバックアップが無い」のと同じ
  - 完了の定義: 設定画面またはダッシュボードに「最終バックアップ成功日時」を表示。24〜48時間以上失敗が続いたら通知またはバッジ表示
  - 依存: P1-2

- [ ] **P1-4: ➕ マイグレーションのテストをCIに固定化**
  - なぜ: V-4で1回検証しただけでは不十分。今後のスキーマ変更のたびに壊れていないかを機械的に保証する必要がある
  - 完了の定義: 各マイグレーションバージョンについて`MigrationTestHelper`ベースのテストを追加し、以降のスキーマ変更はこのテストが通らない限りマージしない運用にする
  - 依存: V-4

**🛑 チェックポイント1**: 実際に端末を初期化またはアプリを再インストールし、バックアップからの復元が実際に機能することを一度は手動で確認する。ここまでやって初めて「Data-Permanent要件が名目でなく実質的に充足された」と言える

## フェーズ4: 正確性修正(テストがある状態で初めて着手)

- [ ] **P4-1: 🔧 和暦マスタの整備**

  - 依存: V-3

- [ ] **P4-3: 🔧 スレッドセーフ化(方式を明確化)**
  - なぜ: `InMemoryVectorIndex`と`GeminiClient.lastCallAt`の競合(§10 #4)
  - 方針: `InMemoryVectorIndex`は読み取り(`topK`)が圧倒的多数・書き込み(`addVector`)が稀なワークロードのため、**Mutexで毎回ロックするのではなく、immutableな配列をAtomicReferenceで差し替える方式を採用する**(検索レイテンシへの影響を避けるため)。`GeminiClient.lastCallAt`はクリティカルセクションが短くレート制御目的なのでMutexで問題ない
  - 完了の定義: 並行アクセステスト(複数コルーチンからの同時topK呼び出し+addVector)が安定して通る
  - 依存: V-3

- [ ] **P4-4: 🔧 N+1クエリ解消**
  - なぜ: `HybridSearchEngine.hybridSearch`と`EntryExporter`のループ内クエリ(§10 #3)
  - 完了の定義: `EntryDao.getByIds`等の一括取得クエリを追加し、ループ内呼び出しを排除。件数を増やした際のクエリ発行回数をテストまたはログで確認
  - 依存: V-3

- [ ] **P4-5: 🔧 SM-2状態導出の改善**
  - なぜ: `srs_review`が履歴のみのため反復回数を間隔日数から推定しており脆弱(§10 #9)
  - 方針: FSRS移行を待たず、**今のうちに`srs_review`へ`repetitionCount`カラムを追加し、レビュー時点の状態をその都度明示的に記録する**形に変更する(推定ロジックへの依存を止める)
  - 完了の定義: 新規カラム追加のマイグレーション+P3-2テストの拡張(repetitionCountが正しく積み上がることを確認)
  - 依存: P3-2, P1-4(マイグレーションテスト基盤)

## 全体サマリー(コーディングエージェントへの投げ方の目安)

| フェーズ | セッション数目安 | 特徴 |
|---|---|---|
| 0 検証 | 1〜2 | コード変更なし、事実確認のみ |
| 1 データ保護 | 2〜3 | 最優先。ここが終わるまで枕を高くして眠れない |
| 2 セキュリティ | 1〜2 | 軽量 |
| 3 テスト基盤 | 2〜3 | ここを飛ばして4に進まない |
| 4 正確性修正 | 3〜4 | 1タスク=1コミット=1セッション推奨 |
| 5 技術的負債 | 2〜3 | 後回しにしても実害は小さい |
| 6 運用ルール | 1 | コード変更なし、ドキュメント更新のみ |
| 7 機能拡張 | 複数 | 既存のロードマップ(§13旧書)通り |

1セッション1タスクを厳守し、都度コミット・都度レビューする運用を推奨します(以前アドバイスした通り、機能追加と依存関係更新のような性質の違う変更は同一コミットに混ぜない)。
