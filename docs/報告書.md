# Personal Encyclopedia 実装困難点と撤回原因に関する報告書

**作成日:** 2026-08-10
**対象期間:** v12.0設計統合からgit撤回までの全実装セッション
**性質:** 自己振り返り・原因分析・教訓抽出

---

## 第一部：実装で困難だった箇所

### 1. entry統一型＋CTI（Class Table Inheritance）の波及管理

このプロジェクトの心臓部であり、同時に最も変更が危険な箇所だった。

`entry` テーブル1枚に13型が乗り、各型が専用の拡張テーブルを持つ。この構造自体は美しいが、**1つの型に触ると最低5箇所のコードが連鎖的に影響する**。

```
EntryRepository.create*()     → 13型分の生成メソッド
EntryEditScreen               → 13型分のフォーム分岐（when文）
EntryEditViewModel            → 13型分の保存ロジック
EntryTypeSections             → 13型分の表示コンポーネント
EmbeddingTextBuilder          → 13型分のテキスト構築戦略
```

例えば「カスタムフィールドを追加する」という一見単純な変更でも、EntryEntity の metadataJson を触るのか新テーブルを作るのかで、上記5箇所すべての方針が変わる。私はこの波及を十分に追わずにコードを提示し続けた。

**特に困難だった点：**
- `EntryEditViewModel` が800行超の単一ファイルに13型全フォームを集約しており、1型の変更が他型のコンパイルを壊す
- `EntryEditScreen` の `when(type)` 分岐がUIとロジックを密結合させており、型追加時の修正箇所が膨大
- `EntryRepository` の `createWebpage()` 等が `embeddingQueue.enqueue()` を内部的に呼ぶため、リポジトリ層の変更がBrain層の初期化順序に依存する

### 2. Room マイグレーション連鎖の脆さ

v1→v2→v3→v4→v5 の5世代のマイグレーションが既に存在し、それぞれがSQL文字列で書かれている。ここに v5→v6（whiteboard系4テーブル＋wiki_article）を追加しようとした際、以下の問題が連鎖した。

- `MIGRATION_5_6` のSQLで `whiteboard_node` に4つのIndexを貼る必要があり、1つのマイグレーション内で7つのDDLを実行する
- `AppDatabase` の `entities` 配列に5つのEntityを追加し、`version` を6に変更
- `DatabaseModule` に新しいDAOの `@Provides` を追加
- これら3ファイルの**いずれか1つでも欠けるとRoomのコンパイル時検証が失敗する**

実際に起きたこと：`WhiteboardDao` に `getByEntryId` を追加した際に `@Query` アノテーションを付け忘れ、KSPが「abstract DAO function must be annotated」エラーを出した。これはマイグレーションとは無関係だが、**Roomのコンパイル時検証が非常に厳格**であるため、1つのアノテーション漏れがプロジェクト全体のビルドを止める。

### 3. FTS4＋Nグラムの日本語検索

形態素解析器を使わずに日本語全文検索を実現するため、bi-gram分割を採用している。この設計自体は知識庫のコードで完成していたが、以下の点が困難だった。

- `NgramTokenizer.buildFtsQuery()` が生成するFTS4 MATCHクエリのエスケープ処理。ユーザー入力に `"` や `*` が含まれるとFTS4の構文エラーになる
- `SearchDocumentDao.ftsSearch()` で `search_document_fts` と `search_document` を `rowid` でJOINする際、FTS4仮想テーブルのrowidが外部コンテンツテーブルと一致しない可能性
- `EmbeddingQueue.updateSearchDocument()` でFTS4の旧レコードを削除→新レコードを挿入する処理が、`search_document` のUPSERTと競合する

### 4. 接続候補承認フローの「暴走防止」設計

§5.5.3の「自動接続は直接connectionに書かず、candidateに積んで承認を得る」という設計は、概念的には明確だが実装時に以下の判断が必要だった。

- `ConnectionEngine.generateCandidatesForEntry()` が `autoConnectEnabled=false` のときは早期リターンするが、この判定をViewModel層とEngine層のどちらに置くか
- `canonicalA/canonicalB` の計算をアプリ層で行うため、無向接続の重複チェックがSQLのUNIQUE制約ではなくKotlinコードに依存する
- 承認時に `createManualConnection()` を呼ぶが、このメソッド自体が重複チェックを含むため、承認フローとの二重チェックが発生する

### 5. Ktor内蔵サーバー＋Bearer認証

Androidアプリ内にNettyサーバーを埋め込む構成。困難だったのは：

- `LocalServer` が8つのDAOをコンストラクタインジェクションで受け取り、1つのクラスが全APIエンドポイントを持つ（本来はルーティングごとに分割すべきだが、知識庫では単一クラス）
- `embeddedServer(Netty, port)` の返り値型 `EmbeddedServer<*, *>` のジェネリクスがKotlinの型推論と衝突しやすい
- DTO（`EntryResponse`, `SrsReviewRequest` 等）が20個以上あり、`@Serializable` の付け忘れが1つでもあればコンパイルエラー

### 6. マルチステージ採点エンジンの和暦処理

`MultiStageGrader.parseYear()` が近現代5元号（令和〜明治）のみ対応で、設計書が例示する「1600年＝慶長5年」が通らない。これは設計書と実装の乖離であり、修正には元号マスターデータの拡充が必要だが、**どの元号まで含めるか**の判断が難しい（日本の元号は248個ある）。

### 7. Compose UIの大規模画面構築

`DashboardScreen`, `EntryDetailScreen`, `EntryEditScreen` はいずれも300〜800行の単一Composable関数で、以下の問題が複合する。

- `remember`/`collectAsState` の数が20個を超え、リコンポジションの範囲が広い
- `AlertDialog` 内の `LazyVerticalGrid` がスクロール競合を起こす
- `WhiteboardScreen` のパン/ズーム/ドラッグのジェスチャ処理で、`detectTransformGestures` と `detectDragGestures` がイベントを奪い合う

## 第二部：撤回に至った原因の自己分析

### 原因1：ファイル単位で提示し、依存グラフを追わなかった

**これが最大の失敗である。**

私は各ファイルを「このファイルはこうです」と個別に提示したが、**そのファイルが呼ぶ側・呼ばれる側のシグネチャが一致しているかを検証しなかった**。

具体的な例：

| 私が提示したもの | 実際の問題 |
|---|---|
| `EntryTypeSections` で `RichContentView(markdown = ..., onInternalLink = ...)` を呼ぶ | 知識庫の `RichContentView` 相当は `MarkdownText(text = ..., onWikiLinkClick = ...)` であり、パラメータ名が完全に異なる |
| `QuizRepository` で `quizDao.countByQuestion(...)` を呼ぶ | `QuizDao` に `countByQuestion` は存在しない。私が架空のメソッドを参照していた |
| `NavGraph` で `WhiteboardScreen(onBack, onNavigateToEntry)` を呼ぶ | `WhiteboardScreen` のコンストラクタに `viewModel` パラメータがあり、`WhiteboardViewModel` が `SavedStateHandle` から `boardId` を読むが、NavGraphのルート定義に `{boardId}` がなかった |
| `WhiteboardViewModel` で `whiteboardDao.observeAll()` を呼ぶ | `WhiteboardDao` に `observeAll()` はなく、`observeBoards()` が正しい |
| `PersonalEncyclopediaApp` で `runStep()` というsuspend関数を非suspendコンテキストから呼ぶ | `onCreate()` 内で直接 `runStep()` を呼んでおり、`appScope.launch` の外に出ていた |

**本来やるべきだったこと：** ファイルAを提示する前に、ファイルAがimportする全クラスのpublic APIを知識庫から確認し、パラメータ名・型・個数が一致することを検証する。

### 原因2：「v12.0」という大きすぎる変更を一度に導入しようとした

設計書v11.0からv12.0への差分として、以下を同時に実装しようとした：

1. Heptabase型ホワイトボード（4テーブル＋DAO＋ViewModel＋Screen＋ジェスチャ処理）
2. Wikipediaビルダー（1テーブル＋DAO＋ViewModel＋3画面）
3. FSRS移行（アルゴリズム＋SrsRepository改修＋Settings追加）
4. Ollama対応（OllamaClient＋AiModels＋GeminiClient改修）
5. リッチテキスト（RichContentView＋WebView＋HTMLテンプレート）
6. カスタムフィールド（新テーブル＋DAO＋UI）
7. 重複排除5経路
8. 遷移アニメーション高速化
9. AppLogger（可観測性）
10. 段階的初期化（堅牢性）

**10個の機能を同時に導入すれば、コンパイルエラーの組み合わせ爆発が起きるのは必然である。** 実際、エラーログには7ファイル以上のエラーが同時に出現していた。

**本来やるべきだったこと：** 1セッションにつき1機能。ビルドが通ることを確認してから次の機能へ。

### 原因3：知識庫のコードを「正」として扱わなかった

知識庫にはv5の完成したコードがある。これが**唯一の正解**である。しかし私は：

- 知識庫にない `RichContentView` を勝手に作り、既存の `MarkdownText` と置き換えようとした
- 知識庫の `EntryTypeSections` の構造を無視して、`RichContentView` を呼ぶ形に書き換えようとした
- 知識庫の `NavGraph` にないルートを追加する際、既存ルートの引数との整合性を確認しなかった

**本来やるべきだったこと：** 知識庫のコードを1行も変えずに新機能を追加できる方法をまず考える。既存コードの変更が必要な場合は、変更箇所を最小限にし、変更前後の差分を明示する。

### 原因4：エラーが発生した際の対応が対症療法的だった

ビルドエラーが報告されるたびに、私は「この行をこう直してください」と個別に対応した。しかし：

- エラーAを直すとエラーBが露出する（型推論エラーが解決すると、その先の実在しないメソッド参照が露出する）
- 複数ファイルにまたがるエラーの場合、1ファイルずつ直すと全体整合が取れない
- ユーザーが「全部まとめて」と言った時点で、すでに個別修正では追いつかない状態だった

**本来やるべきだったこと：** エラーが3ファイル以上に及んだ時点で、個別修正を中止し、「一度gitで安定版に戻し、そこから1機能ずつ再導入する」ことを提案すべきだった。

### 原因5：ユーザーの「動くものが欲しい」という要求を「設計書の網羅」と取り違えた

ユーザーは繰り返し「実装してください」「全部まとめて」と言った。私はこれを「設計書に書かれた全機能のコードを出すこと」と解釈した。しかしユーザーが本当に欲しかったのは：

> **今この瞬間にビルドが通り、インストールして使えるもの**

だった。設計書の網羅性ではなく、**動くコードの確実性**が優先だった。

## 第三部：数字で見る被害状況

| 項目 | 数値 |
|---|---|
| 私が提示した新規・変更ファイルの総数 | 約45ファイル |
| 実際にビルドエラーを引き起こしたファイル | 7ファイル以上 |
| エラーの種類（重複除外） | 約12種 |
| ユーザーが「わからない」「助けて」と言った回数 | 2回 |
| ユーザーがgit撤回を実行した回数 | 1回 |
| 最終的に知識庫のv5コードと整合していた新規ファイル | 推定60%程度 |

## 第四部：教訓と今後の原則

### 教訓1：1セッション1機能。ビルド確認が gate。

複数の機能を同時に導入しない。1つの機能を実装したらビルドし、通ってから次へ。

### 教訓2：知識庫のコードが唯一の正。

知識庫にないクラス・メソッド・パラメータを参照するコードは書かない。新規追加の場合は、知識庫の既存コードが1行も変わらないことを確認する。

### 教訓3：ファイル提示前に依存を検証する。

ファイルAを提示する前に、Aが呼ぶ全クラスのpublic APIを知識庫で確認する。パラメータ名・型・個数の一致を検証してから提示する。

### 教訓4：エラーが3ファイル以上なら即中止して巻き戻す。

個別修正で追える上限は2ファイルまで。それを超えたら「安定版に戻して再導入」を提案する。

### 教訓5：設計書の網羅性より、動くコードの確実性。

ユーザーが「実装して」と言ったとき、それは「設計書の全項目をコードにすること」ではなく「今動くものを1つ増やすこと」である。

## 第五部：現在の状態と次の一手

### 現在の状態

ユーザーはgitでv5安定版に撤回済み。知識庫のコードがそのままの状態で存在する。v12.0で追加しようとした機能（ホワイトボード、Wiki、FSRS、Ollama等）は**すべて未反映**。

### 次の一手として提案する順序

| 優先度 | 機能 | 理由 |
|---|---|---|
| 1 | バックアップのSAF退避（A-1） | データ保護。コード変更が最小。既存のBackupWorkerにSAF書き出しを追加するだけ |
| 2 | クイズ一覧（C-2） | 既存のQuizDao・QuizBankEntityで完結。新テーブル不要 |
| 3 | タグタップ検索（E-2） | NavGraphにクエリパラメータを追加するだけ |
| 4 | 遷移アニメーション高速化（F-5） | NavHostの引数を4行追加するだけ |
| 5 | FSRS（C-1） | SrsRepositoryのrecordReviewを分岐させるだけ。既存のSM-2は残す |
| 6 | ホワイトボード | 新テーブル4枚が必要。マイグレーションの検証が最優先 |
| 7 | Wikipediaビルダー | ホワイトボードの後に。RichContentViewが前提 |

**この順序で、1つずつ、ビルド確認を挟みながら進める。**

---

## 結び

今回の実装で最も学んだことは、**「正しい設計を正しい順序で実装しなければ、正しい設計は意味をなさない」** ということである。

設計書v11.0は7系統の学習支援システムの知見を統合した優れた文書だった。v12.0の設計も方向的には間違っていなかった。しかし、それを**一度に全部コードにしようとした**ことが、すべてのエラーの原因だった。

ユーザーがgitで撤回した判断は正しい。私も同じ判断をすべきだった。

次に進めるときは、**1機能・1ビルド・1確認**の原則を守る。
