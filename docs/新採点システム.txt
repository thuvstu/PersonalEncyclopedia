| 技術                     | 見るもの       | 役割                       |
| ---------------------- | ---------- | ------------------------ |
| **複数Embedding**        | 意味的類似性     | 模範解答との意味的近さ              |
| **Keyword / phrase**   | 明示的な語      | 必須語・専門用語の確認              |
| **Rubric分解**           | 採点項目       | 「何を満たせば何点か」を明確化          |
| **Concept extraction** | 概念         | 回答に必要な概念が存在するか           |
| **NLI**                | entailment | 学生の記述が正しい内容を含意するか        |
| **Contradiction**      | 矛盾         | 模範と逆のことを言っていないか          |
| **Cross-Encoder**      | 文同士の詳細な関係  | Embeddingより精密な比較         |
| **数値・単位検証**            | 数値・式       | LLM/Embeddingではなく決定論的に検証 |
| **構造解析**               | 因果・比較・条件など | 関係性の正しさ                  |
| **極性/否定スコープ**          | 肯定・否定      | 「A」と「Aではない」を区別           |
| **Confidence**         | 判定の確信度     | 難しい回答をLLMに回す判断           |

特に重要：否定・極性

ここは独立した評価軸にする。

例えば、

日本はプレート境界に位置する。

と

日本はプレート境界に位置しない。

はEmbeddingもキーワードも非常に似る。

したがって、

concept:
  日本
  プレート境界に位置する


polarity:
  POSITIVE / NEGATIVE

まで抽出する。

さらに、

～ない
～ではない
～わけではない
～とは限らない
～ではなく～
～以外
～できない
～する必要はない

などの否定スコープを見る。

単純な「否定語が存在するか」ではなく、

どの命題に否定が作用しているか

を見る。さらに一般化すると

   否定だけでなく、**Embeddingが苦手な「関係の反転」**を別処理にする。

   例えば、

   A → B
   B → A


   10 → 100
   100 → 10


   AよりBが大きい
   BよりAが大きい


   AがBの原因
   BがAの原因


   Aの場合
   Aでない場合

   こういうものは、文章全体の意味はかなり近いのに採点上は全く違う。

   したがって、

   Embedding = 内容が似ているか

   構造解析/NLI = その内容を正しく述べているか

   と役割分担させる。

例えば最終LLMには、

Rubric 1:
  必須概念A: 検出
  Embedding: 0.93
  Entailment: 0.96
  Contradiction: 0.02
  Polarity: 一致


Rubric 2:
  必須概念B: 検出
  Embedding: 0.89
  Entailment: 0.54
  Contradiction: 0.71
  Polarity: 逆


Rubric 3:
  数値: 20 m/s
  正解: 72 km/h
  単位変換後: 一致


総合confidence: 0.87

のような構造化された証拠を渡す。

そして、

「では何点か？」

という最終判断をLLMにさせる。

これならLLMがEmbeddingの数値だけ見て、

「まあ似てるから正解！」

となる危険をかなり減らせる。


   優先順位をつけるなら

   最初に実装する価値が高い順は、

   複数模範解答Embedding
   Rubric分解
   Keyword / phrase
   否定・極性・否定スコープ
   NLI / Contradiction
   数値・単位・式の決定論的検証
   Concept extraction
   Cross-Encoder
   Confidence / defer
   最終LLM judge

モデル選定

## 推奨構成

### メインEmbedding：Qwen3-Embedding-4B

[Qwen3-Embedding-4B](https://huggingface.co/Qwen/Qwen3-Embedding-4B?utm_source=chatgpt.com)

これを**PKMのメインEmbedding**にする。

理由はかなり明確で、

* 4B
* 32K context
* 100+言語
* 日本語対応
* 最大2560次元
* Matryoshka対応で次元を削れる
* instruction-aware
* MTEB Multilingual **69.45**
* 0.6Bの64.33からかなり伸びる
* 8Bの70.58にはそこまで大差ない

というバランス。公式比較では4Bが69.45、8Bが70.58なので、**8Bに対して約1.1ポイントしか差がない**。([huggingface.co](https://huggingface.co/Qwen/Qwen3-Embedding-4B?utm_source=chatgpt.com)) ([Hugging Face][1])

つまりAndroidで無理して8Bにするより、

> **4Bを高品質量子化して常駐**

のほうがPKMとしては合理的。

---

# ただし「最強を狙う」なら8B

[Qwen3-Embedding-8B](https://huggingface.co/Qwen/Qwen3-Embedding-8B?utm_source=chatgpt.com)

端末が**RAM 16～24GB級**なら、8Bも候補。

Qwen3 Embeddingシリーズは0.6B / 4B / 8Bで、8Bは4096次元まで出せる。100+言語、32K context、instruction-aware、MRL対応。([huggingface.co](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B?utm_source=chatgpt.com)) ([Hugging Face][2])

MTEB Multilingualは、

```text
0.6B    64.33
4B      69.45
8B      70.58
```

なので、

**0.6B → 4B：かなり大きな改善**

**4B → 8B：改善は小さくなる**

という関係。

だから俺なら、

```text
8GB RAM   → 0.6B
12GB RAM  → 4B Q4
16GB RAM  → 4B Q5/Q6 or 8B Q4
24GB RAM  → 8B Q5/Q6
```

くらいを目安にする。

ただしAndroidでは**モデルサイズ＝必要RAMではない**ので、実機ベンチマークは必要。

# そして「検索用」と「採点用」は分ける

ここが今回の用途では重要。

PKMの通常検索：

```text

      ↓
Qwen3-Embedding-4B
      ↓

      ↓

```

ならこれでいい。

しかし**採点**では、

```text

```

を比較する。

ここではEmbeddingだけでなく、

```text

      +
NLI
      +
Cross Encoder / Reranker
      +
否定・数値・構造解析
```

にする。

# RerankerもQwen3シリーズで揃える

ここがかなり良い。

**Qwen3-Reranker-4B**

または端末が強ければ

**Qwen3-Reranker-8B**

を第二段階にする。

Qwen3シリーズはEmbeddingだけでなく、0.6B / 4B / 8BのRerankerも用意されている。しかもEmbeddingとRerankerの両方がinstruction-aware。([huggingface.co](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B?utm_source=chatgpt.com)) ([Hugging Face][2])


```text
             Qwen3-Embedding-4B
                     ↓
              候補検索 Top-20
                     ↓
             Qwen3-Reranker-4B
                     ↓
                Top-3
                     ↓
              最終LLM Judge
```

という構成ができる。

**Embeddingを「検索」、Rerankerを「精密比較」にする。**

これはPKMでも採点でも非常に綺麗。

## EmbeddingGemma-300M
これは性能だけならQwen3-4Bには負けるが、**Androidへの実装容易性では圧倒的に強い**。

Googleが明確にmobile/on-deviceをターゲットにしている300Mモデルで、100+言語対応。([ai.google.dev](https://ai.google.dev/gemma/docs/embeddinggemma/model_card)) ([Google AI for Developers][3])

しかもLiteRT版では、Samsung Galaxy S25 Ultraで、

```text
NPU
256 tokens
7.8 ms
224 MB RSS
182 MB model
```

という実測値が公開されている。

512 tokensでも18ms。1024でも57ms。([huggingface.co](https://huggingface.co/litert-community/embeddinggemma-300m)) ([Hugging Face][4])

> **「とにかくAndroidで常時動かして、検索を一瞬で返したい」**

こともあるのでEmbeddingGemmaもあり。


### 普段のインデックス作成

```text
                    文書
                     ↓
              chunk / metadata
                     ↓
          Qwen3-Embedding-4B
                     ↓
              2560d / 1024d
                     ↓
                 SQLite
                     ↓
              vector index
```

ただし**2560dを必ず使う必要はない**。

Qwen3-EmbeddingはMRLなので、例えば1024dまで落としても性能とストレージのバランスがかなり良い。

数百万chunkを保存するなら次元数は結構効いてくる。

# 採点

採点はさらに別系統。

```text
学生回答
   │
   ├── Embedding ──────┐
   │                    │
   ├── Keyword ────────┤
   │                    │
   ├── Concept ────────┤
   │                    │
   ├── NLI ─────────────┤
   │                    │
   ├── Contradiction ───┤
   │                    │
   ├── Polarity ────────┤
   │                    │
   ├── Numeric ─────────┤
   │                    │
   └── Structure ───────┘
                        ↓
                 Rubric features
                        ↓
                 Qwen Reranker
                        ↓
                  Local LLM
                        ↓
                    最終採点
```

ここでは特に**Embeddingを最終判定にしない**。

| 超高精度rerank     | Qwen3-Reranker-8B              |
